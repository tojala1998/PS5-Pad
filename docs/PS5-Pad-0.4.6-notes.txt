PS5 Pad 0.4.6 (build 12), controller service 2.3

The owner installed 0.4.5 and reported that both lock/unlock and closing/reopening
left the app Offline or Paused in the background. USB verified build 11. Its
new process diagnostics recorded zero automatic connection attempts, while
the connection status file still described the previous background pause.
A subsequent read confirmed zero attempts in the new process and verified that
the saved console preference was still present; the saved address was not lost.

Review identified two ways startup could be dropped before any network request:
scene activation was gated by the process-wide UIApplication state, and an early
rejected start consumed the generation used to permit the first connection.
The existing diagnostics did not capture callback ordering, so they establish
the missing attempt rather than which of these two paths occurred on the phone.

This build uses the scene's activation/deactivation events to control foreground
work. Activation is reconciled on the main queue after view setup. A premature
start cannot consume the foreground attempt, and suspension invalidates queued
activation work. Lifecycle diagnostics identify each running process and record
activation, suspension, attempted startup and reasons for deferring it.

The 0.4.5 session policy remains: connect automatically to a saved console, reuse
a controller after fresh successful status, and initialize once only when the
status confirms no controller exists. Connection retries are bounded. A busy,
unrecognized or permission-blocked service prevents automatic service loading.
Explicit Disconnect remains stopped until another connection action or launch.

No PS5 helper replacement is needed. Controller service 2.3 keeps the virtual
controller separate from the phone's TCP connection. No phone settings or app
data are reset. Bundle identifier remains com.uhnmeyker.ps5pad.

Local lifecycle, protocol, input, discovery, UIKit contract and native ARM64
build checks passed. The standalone 0.4.6 build 12 installation was verified over
USB. The owner confirmed both lock/unlock and closing/reopening work automatically
with Kodi responding. The latest read-only snapshot marks the controller reused,
with one connection attempt, no service load and zero report failures. The process
also records one initialization during the test run; this is not a claim that
the entire run contained zero initializations. Automatic absent-controller/service
startup and long-duration TV-side inactivity still need separate live tests.
Automatic force-quit cleanup during suspension cannot be guaranteed; contextual
keyboard input is not included.
